# Two ways to write Vuka

A Vuka app can be written as `.vuka` files or as plain Go. Both call the
same libraries — [web](/web/), [ui](/ui/) and the [ORM](/orm/) — and run
the same code: a page, a route or a model behaves the same whichever way it
was written.

The switch at the top of the sidebar picks which one the code samples show.
The choice is remembered in this browser, and `?style=go` or `?style=vuka`
in a link opens a page with that choice.

## Vuka

A `.vuka` file is Go with a few additions: decorators that register routes,
pages and services, JSX for markup, attributes on fields, `Result`, `?` and
`match`. The `vuka` command turns each file into Go as it builds.

```vuka
@web.Live("/counter")
type Counter struct {
	ui.Live
	Start int // ?start=3
	n     int
}

@ui.Mount
func (c *Counter) mount(ctx context.Context) error { c.n = c.Start; return nil }

func (c *Counter) Inc() { c.n++ }

func (c *Counter) Render() ui.Node {
	return <div><output>{c.n}</output><button onClick={c.Inc}>+</button></div>
}
```

## Go

The same page in plain Go: registrations are calls, markup is `ui.HTML`
— HTML whose holes are labelled with the Go of their values, the values
after it — and attributes are values passed to a schema method
(`LiveSchema` for a live page, `Schema` for a model).
`go build` and `go run .` build it; the `vuka` command is not needed.

```go
type Counter struct {
	ui.Live
	Start int // ?start=3
	n     int
}

func NewCounter() *Counter { return &Counter{} }

func (c *Counter) LiveSchema(l *ui.LiveSchema) { l.Mount(c.mount) }

func (c *Counter) mount(ctx context.Context) error { c.n = c.Start; return nil }

func (c *Counter) Inc() { c.n++ }

func (c *Counter) Render() ui.Node {
	return ui.HTML(`<div><output>{c.n}</output><button onClick={c.Inc}>+</button></div>`, c.n, c.Inc)
}

func init() {
	web.Routes.Live("/counter", NewCounter)
}
```

| `.vuka` | Go |
|---|---|
| `@web.Get("/pets/{id}")` on `ShowPet` | `web.Routes.Get("/pets/{id}", ShowPet, web.Params("id", "store"))`, or `app.Get(…)` in `main` |
| `@web.Live("/x")` on a type | `web.Routes.Live("/x", NewX)` |
| `@web.Service` on a type | `web.Routes.Service(NewX)` |
| `@ui.Island(opts…)` beside a route | the route's option: `ui.Island(opts…)` |
| `Q string @ui.Bind @ui.URL("q")`, `@ui.Mount` on a method | `l.Field(&p.Q, ui.Bind{}, ui.URL("q"))`, `l.Mount(p.mount)` in `func (p *X) LiveSchema(l *ui.LiveSchema)` |
| JSX: `<li>{x}</li>` | `` ui.HTML(`<li>{x}</li>`, x) ``; `ui.Each`, `ui.If` for lists and conditions — or a `.vuka.html` [template](/ui/templates) |
| `<Sales title="Week" />` | `Sales{Title: "Week"}`: a component is a struct, and a `ui.Node` itself |
| `type Post struct { orm.Base[Post] … }` | `type Post struct { orm.Model[Post] … }` |
| `Title string @orm.Char{Max: 200}` | `s.Field(&p.Title, orm.Char{Max: 200})` in `func (p *Post) Schema(s *orm.Schema)` |
| `Post.Objects`, `Post.Title` | `orm.Objects[Post]()`, `PostFields.Title` (generated by `go generate`) |
| `@orm.Transaction`, `@orm.TxOn("main")` | `orm.Transaction(ctx, func(ctx context.Context) error { … }, orm.TxOn("main"))` |
| `decorator logged(c) { … }`, `@logged` on `save` | `func logged(c *vuka.Call)`, `var save = vuka.Wrap(saveImpl, vuka.FuncInfo{Name: "save"}, logged)` |
| `static Limit = 10`, `func Post.Live()` | `var PostLimit = 10`, `func PostLive()`: package-level, named after the type |
| `area(c Circle)`, `area(r Rect)` | `areaCircle`, `areaRect`: each overload has its own name |
| `Result[T]`, `?` | `(T, error)` and `if err != nil` — `vuka.Result[T]` works too |
| `Option[T]` | `(T, bool)` or a pointer — `vuka.Option[T]` works too |
| `match` | `switch`, or a type switch |
| `enum Status { Draft, Sent }` | `type Status int` and its constants, `StatusDraft`, `StatusSent` |

## Templates beside Go

Markup can also live in a `.vuka.html` file next to the Go. A component is
a struct whose fields are its props; `sales.vuka.html` is the markup of
the type `Sales`, declared in `sales.go`, and reads its fields by bare
name:

```go
// sales.go
type Sales struct {
	Title    string
	Week     []int
	Children ui.Node
}
```

```html
<!-- sales.vuka.html -->
<section class="sales">
  <h2>{Title}</h2>
  for _, d := range Week {
    <span class="day">{d}</span>
  }
  {Children}
</section>
```

For a live page the file is its `Render`: `counter.vuka.html` holding
`<output>{n}</output><button onClick={Inc}>+</button>` compiles to the
`ui.HTML` call above. The `vuka` command compiles templates as it builds;
for a plain `go build`, `go tool vuka gen -inplace ./...` (or a
`//go:generate` line) writes each as `x_html.go` beside it. See
[Templates](/ui/templates).

## The same runtime

`.vuka` adds syntax and nothing else. What a decorator, a JSX element or an
attribute does is a call on the libraries' public API, and the transpiler
writes the Go a person would write against it. Nothing in a `.vuka` file
reaches a hidden part of the runtime, so anything a `.vuka` app does, a Go
app can do with the same calls.

What only makes things faster stays separate: the ORM's row scanners and
typed fields, live render tracking and island types are generated files
(`go generate`) that both kinds of app use, and both work without them.

## Eject

`vuka eject` writes the Go for `.vuka` files beside them, and `vuka eject
-rm ./...` deletes the `.vuka` files and keeps their Go as the source: each
file's markup functions become templates in `x.vuka.html`, compiled to
`x_html.go`, and the rest is `x.go` — a plain Go module that builds with
`go build` and behaves as before. See
[eject](/tools/cli#eject).

## Mixing both

`.vuka` and `.go` files live side by side in one package and call each
other. A team can write models in Go and pages in `.vuka`, keep a Go
package of routes next to `.vuka` ones, or move a file from one form to the
other at any time: the app registers the same routes either way.

Checks work for both. `vuka build` reports errors with codes at the `.vuka`
line; a Go app gets the same checks from [`vukavet`](/tools/vukavet), run by
`go vet`.

## Writing these docs

Pages show a sample for each preference in containers:

````md
::: vuka
```vuka
@web.Get("/pets")
func ListPets(store *PetStore) Result[[]Pet] { return store.All() }
```
:::

::: go
```go
func ListPets(store *PetStore) ([]Pet, error) { return store.All() }

func init() { web.Routes.Get("/pets", ListPets) }
```
:::
````

Inline text can follow it too, with `<span class="vuka-only">…</span>` and
`<span class="go-only">…</span>`, and a container can hold prose, tables and
several samples. A sample without a container shows for both — right for
what is the same either way: shell commands, TOML, HTML output.

Every Go sample a page shows under Go is compiled: each fence is a file,
needs no `package` clause or imports (they are added for the names it
uses), and sees the declarations of the page's other Go samples, so a page
declares `Post` once and uses it after. Two marks help:

- `<!-- go:fragment -->` on the line before a fence marks a sample that is
  statements, not declarations: it is checked as a function's body, with
  `ctx` in scope and `return err` allowed.
- `<!-- go:context`, then Go, then `-->` on a line of its own, declares what
  the samples use without the page showing it — a store type, a model
  defined on another page.

`go test ./docs -run TestGoSamples` from the repository root type-checks and
vets them against the libraries, and fails on what only a `.vuka` file has
(decorators, `?`, `match`, JSX, `Post.Objects`); `-pages='web/*.md'`
checks some pages only.
